# Data Distillery
## October 16, 2026 Release

The following release notes discuss the initial release of the Data Distillery context of the UBKG
in the [JSON Knowledge Graph](https://github.com/x-atlas-consortia/json-knowledge-graph) (JKG) format.


## Contexts
The [UBKG download site](https://ubkg-downloads.xconsortia.org/) contains files related to three distinct UBKG-JKG contexts:
### UMLS
This context contains data extracted from the [2026AA](https://www.nlm.nih.gov/pubs/techbull/mj26/mj26_umls_aa_release_notes.html) release of the UMLS.

### base
The [base context](https://ubkg.docs.xconsortia.org/contexts/#ubkg-base-context) appends to the UMLS context data from 22 
SABs. Where applicable, SAB source data was refreshed from sources.

### Data Distillery (base + 39 SAB)
The [Data Distillery context](https://ubkg.docs.xconsortia.org/contexts/#data-distillery-context) appends to the base context
data from 39 SABs. 
The KF SAB corresponds to its most recent update in Globus.

## Formats
Each UBKG-JKG context is available in two forms:
* a Zip of the turnkey Docker distribution host of neo4j
* a Zip of the JKG JSON file used to build the Docker distribution

The DDKG JKG JSON is a single file that requires over 31 GB.
The corresponding Docker/neo4j distribution requires over 81 GB.

# JKG model and Cypher

As the documentation on the JKG specification describes, the JKG data model differs significantly from the UBKG model. 
Many data elements that are nodes and distinct relationships in the UBKG model are now properties in JKG. 
Cypher queries that work against a UBKG instance in UBKG format will need to be converted to work against a similar UBKG instance in JKG format.

The [concept subgraph](https://ubkg.docs.xconsortia.org/datamodel/#the-concept-subgraph) of the UBKG that linked each Concept node with a set of Code, Term, Definition, and Semantic Type nodes
has been replaced with a simpler architecture in the [JKG model](https://github.com/x-atlas-consortia/json-knowledge-graph#jkg-data-model). 
In particular, 
* A "code" (representation of a concept in a SAB) no longer has its own node, but is the [codeid](https://github.com/x-atlas-consortia/json-knowledge-graph#concept-term-code) property of the CODE relationship between a Concept node and a Term node. 
* In addition to representing a code in a SAB, a CODE relationship (or coderel) describes a code's term type with a property. 
* Definitions are now properties of Concept nodes.

## Semantic types
Semantic Types for Concepts are represented as additional labels of type [Node_Label](https://github.com/x-atlas-consortia/json-knowledge-graph#node_label) for Concept nodes. 
Although there are distinct Node_Label nodes for Semantic Types, the Node_Label node hierarchy is separate from the Concept node hierarchy.

Because Semantic Types contain spaces (e.g., "Neoplastic Process"), queries that work directly with node labels  other than "Concept"  must employ backticks (`). 

## Identifiers for CUIs
Unlike the UBKG, identifers for minted concepts in JKG do not contain the string "CUI" as suffix. For example, if a node with id UBERON:XXX is assigned a minted concept, the concept ID is UBERON:XXX, not UBERON:XXX CUI.
UMLS CUIs include a prefix of "UMLS"—in other words, the format of a UMLS concept identifier is UMLS:CUI, not CUI.

## Analytical files

The [UBKG-JKG generation framework](https://github.com/x-atlas-consortia/ubkg-jkg-generation) (ETL) generates a number of analytical files as it ingests a SAB into the JKG.

There are two types of analytical files
* [generation](https://github.com/x-atlas-consortia/ubkg-jkg-generation/blob/main/README.md#analytic-outputs)
These files are generated as the content of a SAB's [JKGEN](https://github.com/x-atlas-consortia/ubkg-jkg-generation#jkg-edgenode-jkgen-format) (JKG edge node) files is imported into the JKG JSON. 

* [comparison](https://github.com/x-atlas-consortia/jkg-neo4j/blob/main/scripts/README.md#compare_jkg_json)--files generated by comparing the JKGEN files of a SAB with the corresponding JKG neo4j instance.

[This folder path in Globus ](https://app.globus.org/file-manager?origin_id=24c2ee95-146d-4513-a1b3-ac0bfdb7856f&origin_path=%2Fprojects%2Fdata-distillery%2FDistributions%2FDataDistillery%2F)contains the analytical files for the SABs of the latest Data Distillery release, along with the JKGEN files for each SAB.  
[This spreadsheet](https://docs.google.com/spreadsheets/d/1U7mKLN65cLWqcwFn_xVKxwK5sJr8JkEW07EaY09B3bE/edit?usp=sharing) summarizes the ingestions, showing the results of analysis.

For the initial release, every SAB's data was tested both during generation and then in comparison with the JKG neo4j instance.

# Variances in SABs

## Self-referential edges
_Self-referential edges_  start and end with the same Concept. 

The majority of self-referential edges in SABs are explicitly asserted in the edge file--in other words, they are not artifacts of transitive cross-referencing. 

For the case of SABs that are OWL files, self-referential edges may be a result of the PheKnowLator script. 
For SABs that are in UBKG edge/node format, self-referential edges may simply be poor design. 

The JKG ETL excludes self-referential edges from import. (The JKG framework also excludes self-referential edges from UMLS.)

## Obsolete UMLS CUIs
Some SABs refer to [obsolete UMLS CUIs](https://github.com/x-atlas-consortia/ubkg-jkg-generation/blob/main/docs/Obsolete%20Concepts.md) in node cross-references or edges. 
The JKG ETL does not reify obsolete UMLS concepts; instead, it mints new concept identifiers. 
For example, if a node with code SAB1:X is assigned to an obsolete UMLS concept, the script assigns it a concept with id SAB1:X. 
The ETL also excludes edges that refer to obsolete concepts.

## Duplicate node labels
In some SABs, multiple nodes have the same node label. 
The JKG ETL replicates this node label duplication in the JKG. 
Duplication of node labels appears in some SABs (notably, GLYCANS and DGN) to be an overloading of the node label field as a type of node categorization that should really be represented with explicit assertions (e.g., isa).
