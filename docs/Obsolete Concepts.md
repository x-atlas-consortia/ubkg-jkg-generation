# UBKG-JKG: Obsolete Concepts

# CUI obsolescence
As the UMLS and SAB vocabularies evolve, concepts can become obsolete. In some cases,
a concept may be replaced with another concept. In the UMLS, a concept that is replaced is 
described as being _merged_ with another. 

## UMLS CUI obsolescence
The UMLS does not delete obsolete concepts between releases; instead, it maintains a history of changes.
1. Obsolete CUIs are flagged in MRCONSO.RRF.
2. The UMLS maintains a historical reference for CUIs in a [file set](https://www.nlm.nih.gov/research/umls/licensedcontent/umlsknowledgesources.html) that is separate from the file set of a UMLS release.

## SAB CUI obsolescence
In general, a SAB's owner does not make available histories of changes to concept identifiers. 

# SAB references to obsolete CUIs
SABs often refer to obsolete CUIs. In particular, the JKGEN files generated by the **sab2jkg** script can
refer to obsolete CUIs as follows:

1. The node file can include an obsolete CUI as a cross-reference in the _node_dbxrefs_ column.
2. The edge file can refer to an obsolete CUI as the subject or object of an assertion.

# UBKG-JKG ETL workflow

The components of the UBKG-JKG ETL workflow address the issue of obsolete CUIs.

## Explicit logic

### umls2jkgen
The **umls2jkgen** script does not import UMLS CUIs that are flagged as being either obsolete or suppressed in MRCONSO.RRF.

### jkgen2jkg
The **jkgen2jkg** script verifies whether a UMLS CUI referenced in a JKGEN file exists in the JKG JSON.

1. If a node in the node file cross-references an obsolete CUI, the script replaces the CUI with a CUI minted from the node identifier.
2. The script ignores an edge in the edge file that refers to an obsolete CUI as either the subject or object of an assertion.

## Implicit logic

Because the ingestion of a SAB from JKGEN files is complete and not incremental, 
a CUI that becomes obsolete in a SAB simply disappears when the SAB's JGKEN files are updated and the JKGEN files are used to import the SAB into the JKG JSON.

# UMLS CUI Merges: loss of information vs. change in information

Because the UBKG-JKG ETL ignores obsolete concepts, the content of 
a JKG instance for a SAB may differ from the content of the JKGEN files. 
In particular, 
* A SAB node's CUI reference may change between releases of the UMLS. For example, the equivalence algorithm may change the "assigned CUI" for a node from a UMLS CUI to a minted CUI. 
* An edge in a SAB's JKGEN edge file may not have a corresponding relationship in the JKG.

The exclusion of edges with references to obsolete CUIs, in particular, constitutes a loss of information from a SAB. 
This loss is usually valid, but there are ambiguous cases.

If a CUI were considered unambiguously obsolete, then the corresponding loss of information
would be unambiguously valid. For example, if a CUI encodes a discontinued medication, then an assertion
involving the CUI would no longer be valid.

For the case of a UMLS CUI that is merged, the state of edge information is more complicated.
* If the new CUI has the same scope as the obsolete CUI, then it could be argued that the edge still has 
transitive validity.
* If the new CUI has different scope than the obsolete CUI, then the edge's assertion may no longer be valid for the new scope. For example, if a concept encoding a specific disease is merged with the concept that encodes a more general disease, then an assertion involving the specific condition may not be valid for the more general one.

Regardless of the scope of a merger, if an obsolete concept were simply replaced in an assertion with the concept with which it was merged, 
the information of an assertion that originally referred to the obsolete concept would change. Simple replacement of concepts 
would thus be incorrect because it would change the original assertions that involved the obsolete concept. 

The UBKG-JKG ETL does not replace obsolete UMLS CUIs in edges with merged CUIs, but excludes the edges.
